# Wonderfly Inventory System — Schema Reference

This document describes the **cumulative end state** of the Postgres schema as of migration `029_comprehensive_mapping_fixes.sql`. It reflects every column, constraint, trigger, RLS policy and default added across the 29 migration files in `supabase/migrations/`.

The database runs on Supabase (Postgres 15+). The application code references it through `lib/types/database.types.ts`; that file is the source of truth for TypeScript type shapes and was used to corroborate the SQL below.

---

## Schema-Level Notes

### Extensions

```sql
CREATE EXTENSION IF NOT EXISTS "uuid-ossp";
```

`uuid_generate_v4()` is used as the default for every UUID primary key in the schema. No `pgcrypto` is enabled — UUID generation is exclusively `uuid-ossp`.

### Custom Enums

All enums are created in `001_initial_schema.sql`. `event_type` was extended in migration 005.

```sql
CREATE TYPE user_role        AS ENUM ('admin', 'sales', 'staff', 'readonly');
CREATE TYPE booking_status   AS ENUM ('confirmed', 'canceled', 'completed', 'needs_review');
CREATE TYPE event_type       AS ENUM ('coordinated', 'dropoff', 'pickup', 'willcall', 'arena_pickup');
                                                              -- 'arena_pickup' added in migration 005
CREATE TYPE booking_source   AS ENUM ('webhook', 'manual');
CREATE TYPE item_type        AS ENUM ('equipment', 'sub_item');
CREATE TYPE resolved_action  AS ENUM ('cleared', 'moved_to_oos');
CREATE TYPE webhook_result   AS ENUM ('success', 'error', 'unmapped_service', 'skipped');
```

`equipment_reports.report_type` and `chain_loading_notes.item_type` are plain `text` columns guarded by CHECK constraints rather than enum types.

### Shared Functions

```sql
-- Generic "touch updated_at on UPDATE" handler.
CREATE OR REPLACE FUNCTION set_updated_at()
RETURNS TRIGGER AS $$
BEGIN
  NEW.updated_at = now();
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

-- Returns the role of the currently-authenticated user, used inside RLS USING/WITH CHECK clauses.
-- SECURITY DEFINER + STABLE so it can read users.role without being blocked by the
-- users table's own RLS policies.
CREATE OR REPLACE FUNCTION get_my_role()
RETURNS user_role AS $$
  SELECT role FROM users WHERE id = auth.uid();
$$ LANGUAGE sql SECURITY DEFINER STABLE;
```

Two count-recalculation triggers (`update_issue_flag_count`, `update_out_of_service_count`) keep denormalized counts on `equipment` and `equipment_sub_items` in sync — see those tables for details.

### Permission Grants

`002_grant_permissions.sql` grants `ALL` on every table, sequence and routine in the `public` schema to `anon`, `authenticated`, and `service_role`, plus matching `ALTER DEFAULT PRIVILEGES` so future objects inherit the same grants. This is required because the schema was created via SQL (not the Supabase dashboard), so privileges weren't applied automatically. **RLS is the only thing protecting rows** — the grants do not bypass it.

### Realtime Publications

The following tables are added to `supabase_realtime` so the client receives change events:

```
bookings, equipment, equipment_sub_items, service_mappings,
issue_flag_items, out_of_service_items
```

## Users & Auth

### `users`

Profile rows for every authenticated user. The `id` column references `auth.users(id)` so the row is automatically deleted when the Supabase auth user is deleted. Stores role (drives RLS) and a personal theme preference.

```sql
CREATE TABLE users (
  id         uuid        PRIMARY KEY REFERENCES auth.users(id) ON DELETE CASCADE,
  full_name  text        NOT NULL,
  role       user_role   NOT NULL DEFAULT 'readonly',
  theme      text        DEFAULT 'light'
                         CONSTRAINT users_theme_check CHECK (theme IN ('light', 'dark')),
  created_at timestamptz NOT NULL DEFAULT now()
);
```

`theme` was added in migration 020.

**RLS policies:**
- `SELECT`: a user can always read their own row; admins can read every row.
- `INSERT` / `UPDATE` / `DELETE`: admin only.

**Example row**
```json
{
  "id": "9c4d0e3f-2b8a-4d22-a5b1-1f9c3e7a0b41",
  "full_name": "Jon Millhausen",
  "role": "admin",
  "theme": "dark",
  "created_at": "2026-01-12T14:32:18.114Z"
}
```

## Equipment & Inventory

### `equipment`

The master catalog of rentable inventory items. `id` is a stable text slug (e.g. `foam_machine`, `elite_laser_tag`) generated by hand and used everywhere — `service_mappings.item_id`, `booking_items.item_id`, etc. all reference it as a string. `out_of_service` and `issue_flag` are denormalized counters maintained by triggers (see `issue_flag_items` / `out_of_service_items`).

```sql
CREATE TABLE equipment (
  id                 text        PRIMARY KEY,
  name               text        NOT NULL,
  total_qty          int         NOT NULL DEFAULT 0,
  out_of_service     int         NOT NULL DEFAULT 0,  -- maintained by trigger
  issue_flag         int         NOT NULL DEFAULT 0,  -- maintained by trigger
  is_active          bool        NOT NULL DEFAULT true,
  custom_setup_min   int,
  custom_cleanup_min int,
  categories         text[]      DEFAULT '{}',        -- nullable since migration 025
  created_at         timestamptz NOT NULL DEFAULT now(),
  updated_at         timestamptz NOT NULL DEFAULT now()
);
```

`categories` was added in migration 011 (`NOT NULL DEFAULT '{}'`). Migration 025 dropped the `NOT NULL` and standardized values to the canonical set: `Primary`, `Specialty`, `GameTruck`, `Lawn Games`, `Add-Ons` (empty arrays were converted to `NULL`).

**Triggers:**
- `equipment_updated_at` — `BEFORE UPDATE` calls `set_updated_at()` to refresh `updated_at`.
- `out_of_service` and `issue_flag` are written by `update_out_of_service_count()` / `update_issue_flag_count()` triggers fired on the related child tables.

**RLS policies:**
- `SELECT`: any authenticated user.
- `INSERT` / `UPDATE` / `DELETE`: admin only.

**Example row**
```json
{
  "id": "foam_machine",
  "name": "Foam Machine",
  "total_qty": 6,
  "out_of_service": 1,
  "issue_flag": 0,
  "is_active": true,
  "custom_setup_min": 30,
  "custom_cleanup_min": 20,
  "categories": ["Specialty"],
  "created_at": "2026-01-15T18:02:11.000Z",
  "updated_at": "2026-04-22T13:14:09.221Z"
}
```

### `equipment_sub_items`

Components packed alongside parent equipment (e.g. `blower_motor` under `foam_machine`, `laser_tag_chargers` under `elite_laser_tag`). `parent_id` is kept as a non-null fallback column; the canonical many-to-many relationship lives in `equipment_sub_item_links` (added in migration 010).

```sql
CREATE TABLE equipment_sub_items (
  id             text  PRIMARY KEY,
  parent_id      text  NOT NULL REFERENCES equipment(id) ON DELETE CASCADE,
  name           text  NOT NULL,
  total_qty      int   NOT NULL DEFAULT 0,
  out_of_service int   NOT NULL DEFAULT 0,  -- maintained by trigger
  issue_flag     int   NOT NULL DEFAULT 0,  -- maintained by trigger
  is_active      bool  NOT NULL DEFAULT true
);
```

**RLS policies:** identical shape to `equipment` — any authenticated read, admin write.

**Example row**
```json
{
  "id": "foam_blower_motor",
  "parent_id": "foam_machine",
  "name": "Foam Blower Motor",
  "total_qty": 6,
  "out_of_service": 0,
  "issue_flag": 1,
  "is_active": true
}
```

### `equipment_sub_item_links`

Added in migration 010. Many-to-many junction between `equipment` and `equipment_sub_items`, carrying `loadout_qty` (how many of this sub-item to pack per 1 unit of the parent). Replaces the implicit single-parent relationship in `equipment_sub_items.parent_id` and lets one sub-item be reused across multiple parents.

```sql
CREATE TABLE equipment_sub_item_links (
  id          uuid PRIMARY KEY DEFAULT uuid_generate_v4(),
  sub_item_id text NOT NULL REFERENCES equipment_sub_items(id) ON DELETE CASCADE,
  parent_id   text NOT NULL REFERENCES equipment(id)           ON DELETE CASCADE,
  loadout_qty int  NOT NULL DEFAULT 1 CHECK (loadout_qty > 0),
  UNIQUE (sub_item_id, parent_id)
);
```

The migration backfills one row per existing `equipment_sub_items` record from its `parent_id`.

**RLS policies:** any authenticated read, admin write (mirrors `equipment_sub_items`).

**Example row**
```json
{
  "id": "5b2f7c9e-0d4a-4f6c-9b3a-7e1d2c8a4b9f",
  "sub_item_id": "foam_blower_motor",
  "parent_id": "foam_machine",
  "loadout_qty": 1
}
```

### `issue_flag_items`

Open damage / needs-attention reports. A flag is "active" while `resolved_at IS NULL`. Inserts/updates/deletes here trigger a recount on the parent `equipment.issue_flag` or `equipment_sub_items.issue_flag` column.

```sql
CREATE TABLE issue_flag_items (
  id              uuid          PRIMARY KEY DEFAULT uuid_generate_v4(),
  item_id         text          NOT NULL,
  item_type       item_type     NOT NULL,
  qty             int           NOT NULL DEFAULT 1,
  note            text          NOT NULL DEFAULT '',
  reported_at     timestamptz   NOT NULL DEFAULT now(),
  resolved_at     timestamptz,
  resolved_action resolved_action
);
```

**Trigger:**
- `issue_flag_items_count` — `AFTER INSERT/UPDATE/DELETE` calls `update_issue_flag_count()`. The function sums `qty` across unresolved rows for the affected `(item_id, item_type)` and writes the total to either `equipment.issue_flag` or `equipment_sub_items.issue_flag`.

**RLS policies:**
- `SELECT`: any authenticated user (required for Realtime cross-session sync).
- `INSERT`: admin, sales, or staff.
- `UPDATE`: admin or sales.
- `DELETE`: admin only.

**Example row**
```json
{
  "id": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
  "item_id": "elite_laser_tag",
  "item_type": "equipment",
  "qty": 2,
  "note": "Two blasters not powering on after Saturday's event",
  "reported_at": "2026-05-11T09:14:22.881Z",
  "resolved_at": null,
  "resolved_action": null
}
```

### `out_of_service_items`

Legacy coarse OOS tracking. Used to maintain the integer `equipment.out_of_service` / `equipment_sub_items.out_of_service` counters via trigger. The newer `equipment_oos` table (migration 021) is what the UI / availability calculations actually read.

```sql
CREATE TABLE out_of_service_items (
  id          uuid        PRIMARY KEY DEFAULT uuid_generate_v4(),
  item_id     text        NOT NULL,
  item_type   item_type   NOT NULL,
  qty         int         NOT NULL DEFAULT 1,
  note        text        NOT NULL DEFAULT '',
  return_date date,
  created_at  timestamptz NOT NULL DEFAULT now(),
  returned_at timestamptz
);
```

**Trigger:**
- `out_of_service_items_count` — `AFTER INSERT/UPDATE/DELETE` calls `update_out_of_service_count()`. Sums `qty` across rows where `returned_at IS NULL` for the affected `(item_id, item_type)` and writes to `equipment.out_of_service` or `equipment_sub_items.out_of_service`.

**RLS policies:**
- `SELECT`: any authenticated user.
- `INSERT` / `UPDATE` / `DELETE`: admin only.

**Example row**
```json
{
  "id": "f0c4e2d1-66a1-4be2-9f3a-b7c0d18d8e44",
  "item_id": "bouncer_castle_combo",
  "item_type": "equipment",
  "qty": 1,
  "note": "Side panel torn — at vendor for repair",
  "return_date": "2026-05-20",
  "created_at": "2026-05-04T16:00:00.000Z",
  "returned_at": null
}
```

### `equipment_oos`

Added in migration 021, extended in migration 022 to support sub-items. Detailed out-of-service tracking that the UI uses for availability math. Each row is a single OOS event for either an equipment item **or** a sub-item (the CHECK constraint enforces exactly-one).

```sql
CREATE TABLE equipment_oos (
  id                   uuid        PRIMARY KEY DEFAULT uuid_generate_v4(),
  equipment_id         text        REFERENCES equipment(id)           ON DELETE CASCADE,
                                   -- nullable since migration 022
  sub_item_id          text        REFERENCES equipment_sub_items(id) ON DELETE CASCADE,
                                   -- added in migration 022
  quantity             int         NOT NULL DEFAULT 1 CHECK (quantity > 0),
  issue_description    text,
  expected_return_date date,
  returned_at          timestamptz,
  created_at           timestamptz NOT NULL DEFAULT now(),
  CONSTRAINT oos_item_exactly_one CHECK (
    (equipment_id IS NOT NULL AND sub_item_id IS NULL) OR
    (equipment_id IS NULL     AND sub_item_id IS NOT NULL)
  )
);
```

Active records are those with `returned_at IS NULL`.

**RLS policies:**
- `SELECT`: any authenticated user.
- `INSERT`: admin or staff.
- `UPDATE`: admin or staff.
- (no DELETE policy — deletions blocked at RLS layer; the app marks `returned_at` instead.)

**Example row**
```json
{
  "id": "0e7c1b8d-2f5a-49e6-9b71-83d4c5a26f10",
  "equipment_id": "bouncer_castle_combo",
  "sub_item_id": null,
  "quantity": 1,
  "issue_description": "Vinyl seam separated — sent to inflatable repair",
  "expected_return_date": "2026-05-22",
  "returned_at": null,
  "created_at": "2026-05-09T11:42:08.000Z"
}
```

## Bookings & Schedule

### `bookings`

One row per scheduled job (Zenbooker import or manual entry). `zenbooker_job_id` is the de-duplication key for webhook ingest; manual bookings pass `null`. Times and date are nullable because Zenbooker v3 payloads can omit them (migrations 003, 004).

```sql
CREATE TABLE bookings (
  id                uuid           PRIMARY KEY DEFAULT uuid_generate_v4(),
  zenbooker_job_id  text           NOT NULL,
  customer_name     text           NOT NULL DEFAULT '',
  event_date        date,                                    -- nullable since migration 004
  end_date          date,
  start_time        time,                                    -- nullable since migration 003
  end_time          time,                                    -- nullable since migration 003
  chain             text           REFERENCES chains(id) ON DELETE SET NULL,
  status            booking_status NOT NULL DEFAULT 'confirmed',
  event_type        event_type     NOT NULL DEFAULT 'coordinated',
  source            booking_source NOT NULL DEFAULT 'manual',
  address           text           NOT NULL DEFAULT '',
  notes             text           NOT NULL DEFAULT '',
  linked_booking_id uuid           REFERENCES bookings(id) ON DELETE SET NULL,
                                   -- added in migration 014
  created_at        timestamptz    NOT NULL DEFAULT now(),
  updated_at        timestamptz    NOT NULL DEFAULT now(),
  CONSTRAINT bookings_zenbooker_job_id_unique UNIQUE (zenbooker_job_id)
);
```

> Note: the migration declares `zenbooker_job_id NOT NULL`, but `app/api/bookings/route.ts` inserts manual bookings with `zenbooker_job_id: null`. The `lib/types/database.types.ts` types model the column as nullable. In practice the column does accept NULL in this database (Postgres allows multiple NULLs under a UNIQUE constraint); the migration's `NOT NULL` declaration is effectively superseded — likely dropped manually outside the tracked migration sequence.

`linked_booking_id` (added in migration 014) is a bidirectional pointer between a drop-off booking and its corresponding Wonderfly Games Pickup or Wonderfly Arena Return. The import route sets both sides; availability code uses it to extend the active date range for multi-day drop-offs.

**Triggers:**
- `bookings_updated_at` — `BEFORE UPDATE` refreshes `updated_at` via `set_updated_at()`.

**RLS policies:**
- `SELECT`: any authenticated user.
- `INSERT` / `UPDATE` / `DELETE`: admin or sales.

**Example row**
```json
{
  "id": "3a7c2e10-9b4d-4f88-8a11-26c5d9e0b7a3",
  "zenbooker_job_id": "1748811223040x418227884930115500",
  "customer_name": "Priya Ramaswamy",
  "event_date": "2026-05-23",
  "end_date": null,
  "start_time": "13:00:00",
  "end_time": "16:00:00",
  "chain": "chain_2",
  "status": "confirmed",
  "event_type": "coordinated",
  "source": "webhook",
  "address": "4218 Wisconsin Ave NW, Washington, DC 20016",
  "notes": "Birthday party — 14 kids ages 8-10. Park on driveway.",
  "linked_booking_id": null,
  "created_at": "2026-05-02T15:18:41.000Z",
  "updated_at": "2026-05-09T10:02:22.118Z"
}
```

### `booking_items`

Line items per booking. `is_sub_item = true` rows reference an `equipment_sub_items.id` and carry `parent_item_id` pointing back at the parent equipment row in the same booking; `is_sub_item = false` rows reference `equipment.id` directly.

```sql
CREATE TABLE booking_items (
  id             uuid  PRIMARY KEY DEFAULT uuid_generate_v4(),
  booking_id     uuid  NOT NULL REFERENCES bookings(id) ON DELETE CASCADE,
  item_id        text  NOT NULL,
  qty            int   NOT NULL DEFAULT 1,
  is_sub_item    bool  NOT NULL DEFAULT false,
  parent_item_id text
);
```

**RLS policies:** mirror `bookings` — any authenticated read, admin/sales write.

**Example row**
```json
{
  "id": "b8d4f1e2-3c47-4d9b-a052-7e1f8c2d4905",
  "booking_id": "3a7c2e10-9b4d-4f88-8a11-26c5d9e0b7a3",
  "item_id": "elite_laser_tag",
  "qty": 12,
  "is_sub_item": false,
  "parent_item_id": null
}
```

## Service Mappings (Zenbooker Webhook Integration)

### `service_mappings`

The lookup table that turns a Zenbooker `service_id` (and optional `modifier_id`) into a concrete `equipment.item_id` plus a quantity rule. One row per `(service_id, modifier_id, item_id)` triple — multiple rows per `(service_id, modifier_id)` are allowed so a single bundle option can produce multiple equipment items (e.g. "Full Obstacle Course" → both `warped_wall` and `obstacles_only`).

```sql
CREATE TABLE service_mappings (
  id                      uuid    PRIMARY KEY DEFAULT uuid_generate_v4(),
  zenbooker_service_id    text    NOT NULL,
  zenbooker_service_name  text    NOT NULL DEFAULT '',
  zenbooker_modifier_id   text,
  zenbooker_modifier_name text,
  item_id                 text    REFERENCES equipment(id) ON DELETE RESTRICT,
                                  -- nullable since migration 008 (skip rows have no equipment)
  default_qty             int     NOT NULL DEFAULT 1,
  use_customer_qty        bool    NOT NULL DEFAULT false,
  is_skip                 boolean NOT NULL DEFAULT false,
                                  -- added in migration 008
  notes                   text    NOT NULL DEFAULT ''
);

-- Migration 028: enforce uniqueness of (service, modifier, item) triples.
-- Replaces the original UNIQUE NULLS NOT DISTINCT constraint that was
-- dropped in migration 006. COALESCE handles NULL modifier/item.
CREATE UNIQUE INDEX service_mappings_unique
  ON service_mappings (
    zenbooker_service_id,
    COALESCE(zenbooker_modifier_id, ''),
    COALESCE(item_id, '')
  );
```

Constraint history:
- 001 created `UNIQUE NULLS NOT DISTINCT (zenbooker_service_id, zenbooker_modifier_id)`.
- 006 dropped it to allow multiple equipment items per `(service, modifier)` combo.
- 008 made `item_id` nullable and added `is_skip` (used to silently consume meta-options like "Get a Custom Quote" without producing a booking item or falling through to the name-match fallback).
- 028 de-duplicated the table and added the current unique index that includes `item_id`.

**Use of synthetic IDs:** The Zenbooker v1 API exposes different `service_id` values than v3 webhooks. The v1 import path (`parseV1Job` in `lib/utils/`) emits **synthetic** service/modifier IDs prefixed with `v1:` — for example `v1:water_tag`, `v1:generator`, `v1_lt_elite`. These are inserted into `service_mappings` as if they were real Zenbooker IDs so the same resolution path handles both sources.

**RLS policies:** any authenticated read, admin write.

**Example rows**

A standard "use customer quantity" mapping (modifier carrying a quantity input):
```json
{
  "id": "f3a1c4b8-7d20-4e9f-9b2a-5c0e1d7f8a94",
  "zenbooker_service_id": "1747883952074x309158420488483400",
  "zenbooker_service_name": "Laser Tag",
  "zenbooker_modifier_id": "1750740653415x754500715588878300",
  "zenbooker_modifier_name": "Generator",
  "item_id": "generator",
  "default_qty": 1,
  "use_customer_qty": true,
  "is_skip": false,
  "notes": "add-on: Generator (required if no outlet nearby)"
}
```

## Webhook & Audit Logs

### `webhook_logs`

Append-only audit log of every Zenbooker webhook call. Inserted with `received_at` + `raw_payload` immediately on receipt; `result` and `result_detail` are written after processing. `booking_id` links to the booking that was created or updated as a result.

```sql
CREATE TABLE webhook_logs (
  id               uuid           PRIMARY KEY DEFAULT uuid_generate_v4(),
  received_at      timestamptz    NOT NULL DEFAULT now(),
  zenbooker_job_id text           NOT NULL DEFAULT '',
  action           text           NOT NULL DEFAULT '',
  raw_payload      jsonb          NOT NULL DEFAULT '{}',
  result           webhook_result,
  result_detail    text,
  booking_id       uuid           REFERENCES bookings(id) ON DELETE SET NULL
);
```

**RLS policies:**
- `SELECT`: admin only.
- INSERT / UPDATE: not exposed via RLS — performed by the API route using the **service role key**, which bypasses RLS entirely.

## Reports

### `equipment_reports`

Added in migration 027. Public-facing damage / missing-item submissions from staff (e.g. tablet at warehouse). Inserts are unauthenticated (the form uses the `anon` key). On a successful submit the API also creates an `issue_flag_items` row using the service-role client and sets `flag_created = true`.

```sql
CREATE TABLE equipment_reports (
  id            uuid        PRIMARY KEY DEFAULT uuid_generate_v4(),
  submitted_at  timestamptz NOT NULL DEFAULT now(),
  staff_name    text        NOT NULL,
  equipment_id  text        NOT NULL REFERENCES equipment(id)           ON DELETE CASCADE,
  sub_item_id   text                 REFERENCES equipment_sub_items(id) ON DELETE CASCADE,
  report_type   text        NOT NULL CHECK (report_type IN ('damaged', 'missing')),
  quantity      int         NOT NULL DEFAULT 1 CHECK (quantity > 0),
  note          text,
  flag_created  boolean     NOT NULL DEFAULT false
);
```

**RLS policies:**
- `INSERT`: **public — `WITH CHECK (true)`**. No auth required, by design.
- `SELECT`: any authenticated user.
- `UPDATE`: any authenticated user (so the API can flip `flag_created` after creating the linked flag).
- (no DELETE policy.)

**Example row**
```json
{
  "id": "fa1b2c3d-4e5f-6789-abcd-ef0123456789",
  "submitted_at": "2026-05-12T08:47:11.441Z",
  "staff_name": "Marcus Thompson",
  "equipment_id": "elite_laser_tag",
  "sub_item_id": null,
  "report_type": "damaged",
  "quantity": 2,
  "note": "Two blasters not powering on after Saturday's event",
  "flag_created": true
}
```
