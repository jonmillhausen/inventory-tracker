## 6. PAGES & FEATURES

### Availability (`/availability`)

Equipment inventory vs. bookings for a selected date. Columns: active chains (keyed by chain **id**) + Unassigned + Booked + Remaining + Status. OOS popover, category filters, "Show Booked Only" toggle, chain popup with per-booking equipment.

**Status thresholds** (`remaining` ÷ `total_qty`): `< 0` overbooked · `= 0` sold_out · `≤ 10%` critical · `≤ 30%` low · else available.

**`available_qty` = `total_qty − active OOS`** — inventory only, no booking deduction. `remaining = available_qty − total_booked`.

**Overnight cutoff rule.** A booking counts only on `event_date` (not `end_date`) when **all** of: `event_type = 'coordinated'` AND `end_date > event_date` AND `end_time <= '04:00:00'`. ⚠️ Narrower than v1.1 implied — it does **not** apply to dropoff/pickup/willcall/arena, and it excludes cleanup time (P1-1). The `<=` boundary means exactly 04:00:00 qualifies.

**P0-1 unmapped detection (`64aa132`)** — replaces tier 4's silent skip. ## 9. PACKING LIST LOGIC

### Coordinated vs drop-off

- **Coordinated / pickup** (`COORD_TYPES`): **MAX** quantity across bookings of the same parent on the chain (equipment is reused event to event)
- **Drop-off / willcall** (`DROP_TYPES`): **SUM** (equipment is left on site and accumulates on the truck)

**P0-8(a):** coordinated sub-items shared across **different** parents now **SUM** their contributions — both parents load simultaneously. MAX applies only across bookings of the *same* parent. Pre-fix, 8 chargers were packed where 12 were needed.

**P0-8(d):** coordinated parent quantities **sum the `booking_items` rows within a booking** before taking MAX across bookings (base 10 + add-on 5 = 15, not 10).

⚠️ `arena_pickup` is in **neither** bucket, so arena pickups contribute nothing to a packing list by default-case omission (P2-18, open).

### Sub-item tiered multipliers

Multiplier is resolved from `slugify(equipment.name)` — the **display name**, not the id (`packingList.ts:26-39`):

```
TIER1_SLUGS = { 'bubble_ball', 'elite_laser_tag', 'arrow_tag' }  → max(1, floor(qty / 10))
TIER2_SLUGS = { 'gel_tag', 'laser_tag_lite' }                    → max(1, floor(qty / 20))
default                                                          → qty as-is
```

## 10. DROP-OFF / PICKUP LINKING — AS IMPLEMENTED

⚠️ v1.1 §9 described an algorithm that **is not implemented**. This section describes reality (P0-6 is open and will change it).

**What actually happens, and only in the bulk-import path:**

1. On importing a pickup-type booking with an `event_date`, look up bookings at the **exact same `address`**, with `event_type IN ('dropoff','coordinated')`, `event_date <= pickup date`, ordered by `event_date DESC`, `LIMIT 1`.
2. If found, set `linked_booking_id` bidirectionally.
3. If already linked, the booking **stays `confirmed`** — v1.1 claimed it is flagged `needs_review`. It is not.

**Not implemented:** customer-name extraction from the service name · any lower date bound · **any linking at all on the live webhook path**.

**Availability spanning:** date-level only — a linked dropoff blocks equipment from its `event_date` through the pickup's `event_date`, with both edge days fully blocked.

**Naming convention still expected in Zenbooker** (used by the v1 parser's pickup detection): `"Melissa Brill Lawn Game Pickup"`, `"Obi Ndukwe Lawn Games Pick-Up"`.

## 12. KEY BUSINESS RULES & TECHNICAL DECISIONS

- **Overnight cutoff:** coordinated events with `end_date > event_date` and `end_time <= '04:00:00'` count only on `event_date`
- **Coordinated wins:** if any service on a booking is not a delivery service, the whole booking is coordinated
- **Arena Pickup:** no overlap warnings on Schedule or Audit; 0/0 buffers in availability
- **Full Obstacle Course = 2 items:** maps to both `warped_wall` (1) and `obstacles_only` (1)
- **Webhook over middleware:** Zenbooker → Vercel API → Supabase directly, no Zapier/Make
- **Secret via URL param:** Zenbooker does not support header-based webhook secrets
- **Service mappings live in the DB** (248 rows), admin-configurable, not hardcoded
- **ThemeProvider:** `dark` class on `<html>`, per-user persistence in `users.theme`
- **Google Fonts:** DM Sans + JetBrains Mono as `<link>` tags in `app/layout.tsx` — the Pricing Calculator uses literal font-family names in inline styles and is incompatible with `next/font` hashing
- **Pricing Calculator styling:** inline styles, not Tailwind — preserve as-is

### ⚠️ PATTERN: unbounded `.select()` is a silent-truncation risk

**PostgREST caps every request at 1,000 rows and does not error when a table exceeds it.** An unbounded `.select('*')` quietly returns the first 1,000 rows in physical order; the caller cannot distinguish a truncated result from a complete one.

This produced a production incident on 2026-08-01. `booking_items` crossed 1,000 rows around **2026-06-03** (now 1,384). Seven fetch sites silently dropped ~384 item rows — the most recently written ones. Availability rendered chain time windows correctly (`bookings` = 837, under the cap) while showing **no equipment** for any booking whose items sat past row 1,000. Chain Loading, the 4-Week Audit, Bookings, Schedule, and the print packing list were all affected. Measured:

```
booking_items?select=booking_id  →  content-range: 0-999/1384
bookings?select=id               →  content-range: 0-836/837
```

The unbounded query dated to `40c8a1d` (2026-03-18) and was latent for eleven weeks. It was **not** a Phase 0 regression, despite landing ~8 days before the P0 commits.

**Standard, effective `512c9b1` / `7c0f856`:** every read of a table that can grow goes through `lib/supabase/fetchAll.ts`.

```ts
import { fetchAll } from '@/lib/supabase/fetchAll'

const { data, error } = await fetchAll((from, to) =>
  supabase.from('booking_items').select('*').range(from, to)
)
```

`fetchAll` pages with `.range(from, from + 999)` until a short page returns, with a 5,000-page backstop. It takes a **factory**, not a prebuilt query, so each page is a fresh request.

**Applied at all seven sites:** the packing-list route, the availability/chains/audit/bookings/schedule pages, and `lib/queries/bookings.ts`. The hook matters most — it re-fetches on mount and overwrites the server-rendered payload, so fixing only the server components would have left every page broken in the browser.

**When adding a new read:** if the table can grow past 1,000 rows within a season, use `fetchAll`. A `.limit(n)` with an explicit `.order()` is also fine when truncation is intentional (that is what the webhook-log viewer does).
