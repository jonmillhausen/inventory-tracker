# Wonderfly Inventory Tracker — Knowledge Base Protocol

**Location in repo:** `docs/kb/KB_PROTOCOL.md`
**Purpose:** Keep one canonical, verified description of the system so every Claude chat and every Claude Code session starts from the same context.

---

## 1. Why this exists

KB v1.1 was hand-written from session memory. Four weeks later the June 2026 audit found **26 places where it no longer matched reality** — undocumented tables, wrong sidebar order, a documented linking algorithm that was never implemented, and an entire undocumented `marketing_api` schema. Documentation written from memory drifts silently, in exactly the way this app's data does.

**The rule that fixes it: the KB is generated from verification, not from recollection.**

---

## 2. Where the KB lives

| Location | Purpose | Who reads it |
|---|---|---|
| `docs/kb/WONDERFLY_INVENTORY_TRACKER_KB_v[X.X]_[YYYY-MM-DD].md` | Canonical copy, versioned with the code | Claude Code |
| Claude Project knowledge (Inventory Tracker project) | Same file, uploaded | Planning/review chats |

Both must hold the **same version**. When a new version ships: commit to `docs/kb/`, upload to project knowledge, **delete the previous version from project knowledge** (old versions stay in git history only).

Superseded versions are *not* kept in `docs/kb/` either — git history is the archive. One file, always current.

---

## 3. Naming and versioning

`WONDERFLY_INVENTORY_TRACKER_KB_v[X.X]_[YYYY-MM-DD].md`

- **Minor bump (1.1 → 1.2):** new migrations, new equipment/chains/mappings, new pages or routes, changed calculation rules, corrected drift.
- **Major bump (1.x → 2.0):** architecture change — domain migration, auth consolidation, schema restructure, or a rewrite of how ingestion works.

Every version header carries: version, date, status, what it supersedes, sessions/phases covered, and **the commit hash the KB was verified against.**

---

## 4. When a version bump is REQUIRED

Any session that does one or more of:

- Runs a migration (schema or data)
- Adds, removes, or renames equipment, sub-items, chains, or chain mappings
- Changes service mappings in a way that alters equipment resolution
- Changes a calculation rule (availability, packing, tiers, event-type classification, wizard scoring)
- Adds or removes a page, API route, or environment variable
- Changes integration behavior (webhook events handled, import logic, linking)
- Closes out audit findings that the KB describes incorrectly

Sessions that only add tests, fix typos, or clean dead code do **not** require a bump — note them in the session artifact instead.

---

## 5. How a new version is produced

**Generated by Claude Code with live verification. Never hand-written in chat.**

CC's KB-regeneration procedure:

1. Read the current KB version in full.
2. Read the outstanding delta list (audit §7, or the accumulated notes in session artifacts since the last version).
3. **Verify against reality, not against the old KB:**
   - Live schema, RLS policies, triggers, indexes via Supabase MCP (**SELECT-only**)
   - Live row counts for equipment, sub-items, chains, chain mappings, service mappings, bookings by status
   - Applied migrations from `supabase_migrations`
   - Repo structure, route inventory, env-var references (grep, don't assume)
   - Test count from an actual `npm test` run
4. Rewrite the affected sections. **Describe reality, not intent** — if a documented algorithm isn't implemented, the KB says so and links the finding.
5. Write to `docs/kb/` under the new filename, delete the superseded file, commit.
6. Report to Jon: the new filename, what changed vs. the prior version, and anything found during verification that wasn't in the delta list.

Jon then uploads the new file to project knowledge and removes the old one.

---

## 6. Required sections

A KB version is incomplete without all of these:

1. **Header + how to use** — version, date, verified-at commit, supersedes
2. **System overview** — business, scale, URLs, owner
3. **Tech stack**
4. **Repository structure** — every route and significant file
5. **Database schema** — every live table and column, including legacy/deprecated ones **marked as such**
6. **Equipment inventory** — counts current as of verification
7. **Pages & features** — with the undocumented behaviors (buffers, windows, defaults, coercions)
8. **Zenbooker integration** — events handled, payload fields, mapping resolution, skip patterns, event-type rules
9. **Packing list logic** — coordinated vs dropoff, tiers, multi-parent handling
10. **Drop-off / pickup linking** — as implemented, with any gap between spec and reality called out
11. **Migrations applied** — number, name, and whether tracked in `supabase_migrations`
12. **Key business rules & technical decisions**
13. **Environment variables** — including which are documented-but-unused
14. **Infrastructure & future plans** — including downstream consumers
15. **Sidebar navigation order**
16. **Known issues & open findings** — open P-items from the current audit, with status
17. **Document history**

---

## 7. Standing accuracy rules

- **Mark deprecated things as deprecated** rather than deleting them. `out_of_service_items` belongs in the schema section flagged LEGACY — omitting it is how it stayed invisible.
- **Document the gap when spec ≠ code.** If the KB describes an algorithm that isn't implemented, say "documented but not implemented (see P0-6)."
- **Record counts with their verification date.** "248 service mappings (verified 2026-06-11)" beats "~200+".
- **Name downstream consumers.** The `marketing_api` schema is read by the marketing-agents project — anything that changes it needs a note there.
- **Undocumented defaults are the dangerous kind.** Buffers, windows, fallbacks, and coercions (45-min setup default, 30-min travel fallback, 4am cutoff, 24h staleness window, 08:00–22:00 wizard day) all belong in the KB explicitly.

---

## 8. Session artifacts vs. the KB

| | Session artifact | Knowledge base |
|---|---|---|
| Scope | What happened in one session | How the system works now |
| Lifetime | Superseded by the next one | Superseded by the next version |
| Written by | The planning chat | Claude Code, verified |
| Lives in | `docs/superpowers/artifacts/` + project knowledge (latest only) | `docs/kb/` + project knowledge |

Artifacts accumulate between KB versions and become the delta list for the next bump.
