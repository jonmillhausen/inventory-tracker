## 1. EXECUTIVE SUMMARY

The app's core architecture is sound: auth gating is centralized and consistent, RLS is enabled on every public-schema table, response shapes are uniform, type discipline is good (zero `@ts-ignore`, almost no `any`), and the 146-test suite genuinely covers the happy paths of the three calculation engines.

But the audit confirms the suspicion that motivated it: **the ingestion pipeline is optimized to never bother anyone, and it achieves that by silently producing wrong data.** The live database already shows the consequences:

- **864 `unmapped_service` webhook logs** (9.2% of all logs), with new ones arriving **today** — many are pickup/return jobs violating the naming convention ("Lawn Games Pickup- Katie Mccoy", "Pride Center MD- Arena Return"), which import as equipment-less or wrongly-typed bookings.
- **86 `booking not found` errors**, including **34 lost chain assignments** (`job.service_providers.assigned` for bookings we don't have) and **14 Zenbooker jobs that never produced a booking row at all** — concrete missed events.
- **11 out-of-service sub-item units invisible to availability right now** (`goal_set` 3, `small_black_air_pump` 6, `tripod` 2): sub-item availability reads a trigger-maintained counter, but the trigger watches a legacy table the app no longer writes to.
- **Equipment-level counter drift**: `arrow_tag` counter 0 vs 7 active legacy-table OOS rows; `laser_tag_lite` counter 0 vs 6 active `equipment_oos` rows.
- **39 bookings in `needs_review`** (23 upcoming/undated), surfaced only by a banner on a page nobody is required to open.
- A new service or renamed modifier arriving before a mapping exists produces a **`confirmed` booking with zero equipment, logged as `success`** — the exact missing-truck failure, invisible on every screen.
- Three calculation bugs that produce wrong packed quantities or wrong wizard availability (P0-8).
- An undocumented `marketing_api` schema (6 views) that **reimplements availability math without the overnight, linking, or MAX/SUM rules** and feeds flash-sale eligibility from it.

There are 9 P0 fix specs below. None are large; most are small, isolated diffs with test fixtures already enumerated. The single highest-leverage structural fix is **P0-5 (daily Zenbooker reconciliation)** because it backstops every other ingestion failure.

**Counts:** 9 × P0 · 10 × P1 · 22 × P2 · 14 × P3, plus a 26-item KB v1.2 delta list (§7).

### P0-1. Unmapped services/options produce confirmed, equipment-less bookings logged as `success`

**Problem.** Tier 4 of the mapping resolution ("silently skip") is service-wide, not option-wide. `unmappedNames` — the only thing that triggers `needs_review` — is populated solely by `tryNameFallback`, which runs only for **option-less** services (`lib/utils/webhookProcessor.ts:194-209,328`). For a service *with* options: tier-1 modifier-ID lookup misses, tier-1.5 name match only runs when `option.id === ''` (`:411`), tier-2 base mapping requires existing base rows (`:450`), tier-3 equipment-name fallback does **not** record misses (`:473-481`), and tier 4 is a bare comment (`:483-485`). Result: `status = 'confirmed'`, zero `booking_items`, `result='success'`, `result_detail=null` (`app/api/webhooks/zenbooker/route.ts:332`).

**Evidence (live).** 864 `unmapped_service` rows; the most recent arrived **2026-06-11 19:36 UTC** (today). 12 of them produced no booking at all. Recent details include internal blocks that now exist nowhere ("BLOCKING OFF FOR BALTIMORE PRIDE"), priced add-ons ("Additional 30 minutes of Obstacle Course"), and a steady stream of convention-violating pickups (see P0-6). Note: the existing test `"silently skips unmatched options — price is irrelevant"` (`__tests__/lib/utils/webhookProcessor.test.ts:97`) **enshrines the bug**.

**Fix spec.**
1. In `resolveWebhookItems`, any option reaching tier 4 that is not consumed by an `is_skip` mapping is appended to `unmappedNames` as `"{service_name} / {option.text}"`. (If noise is a concern, restrict to options with `price > 0` plus all options on services that resolved zero items.)
2. Any booking whose services resolve to **zero items overall** — excluding pickup/arena_pickup/admin-skip types — gets `status='needs_review'` and `result='unmapped_service'` with the full unmatched list in `result_detail`.
3. Surface: add an "Unmapped options" count card on Settings → Webhook Logs fed by `webhook_logs WHERE result='unmapped_service' AND received_at > now()-interval '7 days'`, and add result-type filtering to that page (currently fixed at latest-200, no filter — `lib/queries/webhookLogs.ts:20`). The DB already has a ready-made `marketing_api.service_mapping_health` view enumerating services seen in the last 90 days without mappings — reuse the pattern in `public` (or query it) for a daily digest.

**Acceptance criteria.**
- A `job.created` for a service ID with no `service_mappings` rows produces a `needs_review` booking and a `webhook_logs` row with `result='unmapped_service'` listing every unmatched option text.
- A renamed modifier ID on a service WITH a base mapping records a fallback warning in `result_detail` (it currently silently degrades to base `default_qty`, `webhookProcessor.ts:450-466`).
- No booking with `event_type='coordinated'` and zero items can carry `status='confirmed'` out of the webhook or import path.
- Webhook Logs page can filter by result and shows a 7-day unmapped count.

**Jest tests to add (`__tests__/lib/utils/webhookProcessor.test.ts`).**
- `it('unknown service with priced options → unmappedNames contains each option')` — replaces/inverts the test at line 97.
- `it('renamed modifier on service with base mapping → base qty used AND fallback recorded')`
- `it('booking resolving to zero items (non-pickup) → flagged')`
- `it('is_skip-consumed options do NOT appear in unmappedNames')` (regression guard against noise).

### P0-2. Booking writes are unchecked and non-transactional — `success` logged over failed or duplicated item writes

**Problem.** Three classes in one fix:
1. `booking_items` delete + insert results are never checked: `app/api/webhooks/zenbooker/route.ts:285-291` (`service_order.edited`), `:376-382` (`job.created`), import `route.ts:973-979`, `:874`, `:791-792`. Execution falls through to a `success` log either way. The replace is also two separate PostgREST calls — a timeout between them permanently wipes items; interleaved duplicate deliveries can double them (`booking_items` has **no unique constraint** on `(booking_id, item_id)` — verified live: only the PK index exists).
2. Mapping-table fetches discard errors: `route.ts:241-245,312-316`, import `:763-770` destructure only `data`; a failed `service_mappings` select is indistinguishable from "no mappings exist" → per P0-1, every booking resolves to zero items with `success`. During a 500-job re-import this silently strips the entire table.
3. Every `webhook_logs` update/insert is fire-and-forget (15 call sites in the webhook route, 5 in import) — failures leave `result=null`, rendered as "—".

**Fix spec.**
1. Check `error` on both the delete and the insert; on failure set `result='error'` with the Postgres message and return 500 (Zenbooker retries on 5xx).
2. Move the delete+insert into a single Postgres RPC (`replace_booking_items(booking_id, items jsonb)`) so the swap is atomic; add a unique index on `booking_items (booking_id, item_id, is_sub_item)` as a backstop regardless.
3. Check `error` on each mapping/equipment/chain fetch; abort with 500 (webhook) or 502-before-loop (import). Refuse to process if `serviceMappings.length === 0`.
4. If the `webhook_logs` write itself fails, return 500.

**Acceptance criteria.**
- Mock-failed `booking_items.insert` → log row `result='error'`, HTTP 500, booking not left item-less with a success log.
- Mock-failed `service_mappings` fetch → request aborts before any booking write.
- Two concurrent identical `job.created` deliveries → no duplicate `booking_items` rows (unique index holds).

**Jest tests to add** (new `__tests__/api/webhooks.test.ts` with a mocked Supabase client — the webhook route currently has **zero** route-level tests).
- `it('failed items insert → result=error, 500')`
- `it('failed mappings fetch → 500, no booking upsert')`
- `it('duplicate delivery → idempotent item rows')`

### P0-3. Webhook ingress drops authenticated events with zero trace — including the stale-timestamp retry trap

**Problem.** Seven exit paths run before the `webhook_logs` insert at `route.ts:78-87`: bad secret (`:37`), body-read failure (`:46`), >1 MB (`:50`), bad JSON (`:57`), **stale timestamp** (`:61-66`), missing `data.id` (`:70`), failed log insert (`:90`). The stale check rejects anything older than 300 s — if Zenbooker retries a delayed delivery with the *original* timestamp, every retry is rejected forever and the job silently never exists. Conversely, the timestamp check is **skipped entirely when `timestamp` is absent**, so it provides no replay protection either (see P0-9).

**Fix spec.**
1. Log-first: insert the `webhook_logs` row immediately after JSON parse; record pre-validation rejects as `result='rejected'` with a reason (`stale_timestamp`, `missing_id`, `oversize`…). Auth failures (bad secret) may stay unlogged to avoid probe noise, but track a counter.
2. Widen or drop the staleness window (the secret already gates authenticity); 24 h is plenty if kept.
3. Validate the v3 payload with a zod schema (`data.id`, event enum, `services` array shape, `customer.name`, `start_date`, `time_slot`); non-conforming payloads → `result='invalid_payload'` + `needs_review` where a booking already exists, never a silent default. This is the v3-drift defense: today a renamed `services` key yields a confirmed empty booking (`route.ts:318`, `?? []`), a missing `start_date` yields an invisible `event_date=null` booking, and `job.rescheduled` with missing fields **nulls out the existing booking's date** (`route.ts:219-224`) — logged as success.
4. Coerce `option.quantity`/`price` with `Number()` in the v3 `service_selections` path (`webhookProcessor.ts:398` takes it raw; only the `service_fields` branch normalizes — import does coerce, `route.ts:620`).

**Acceptance criteria.**
- Stale-timestamp, oversize, and missing-id requests all leave a `webhook_logs` row.
- `job.rescheduled` missing `start_date` does **not** null the stored date; booking flagged instead.
- String `quantity: "16"` in v3 selections yields qty 16, not a string in the insert.

**Jest tests to add.** Route tests for each reject path asserting a log row; `extractBookingFields` with missing/invalid `start_date` and ms-epoch timestamps; `job.rescheduled` partial payload; string quantities.

### P0-4. Ordering races resurrect canceled bookings and wipe manual fixes

**Problem.** `job.service_order.edited` sets status to confirmed/needs_review unconditionally (`route.ts:240-274`) — a cancel-then-edit sequence re-confirms a canceled event and equipment gets loaded for it. Duplicate/late `job.created` redeliveries upsert over the row (`:343-361`), resetting `status`, re-deriving `chain`, and **hardcoding `notes: ''`** (`:358`) — any admin fix to a `needs_review` booking (chain assignment, items, notes) is silently reverted by the next webhook or bulk import (`import route.ts:945-963`). Reschedules of a linked drop-off don't touch the linked pickup (`:218-238`), corrupting the availability span in both directions. Import vs webhook cancel semantics diverge: import **deletes** canceled bookings (and `ON DELETE SET NULL` strips the partner's `linked_booking_id`, migration 014), webhook soft-cancels — 15 deletions visible in live logs.

**Fix spec.**
1. Status transition guard: `canceled` is terminal for webhook writes unless the incoming action is itself a re-book; `job.created`/`edited` never downgrade `needs_review` decisions silently.
2. On upsert-over-existing, update only fields the event owns; never overwrite `notes`, and never overwrite `chain` if it was set and the payload has no providers. Add a `manually_edited` boolean (set by the bookings PUT route) that webhook writes respect for chain/notes/items.
3. `job.rescheduled` on a booking with a linked pickup: flag the pair `needs_review` (or propagate the date shift).
4. Unify cancel semantics: import soft-cancels like the webhook (keeps audit trail and the link).

**Acceptance criteria.**
- Sequence created → canceled → service_order.edited leaves `status='canceled'`.
- Duplicate `job.created` preserves notes and manually assigned chain.
- Import of a Zenbooker-canceled job sets `status='canceled'`, does not delete.
- Rescheduled drop-off with a linked pickup → pair flagged.

**Jest tests to add.** Route-level sequence tests for each of the four criteria above.

### P0-5. No detection of missed webhooks — build the reconciliation cron

**Problem (confirmed).** No cron, no `vercel.json` schedule, no replay/reconcile code exists. Recovery is the admin-triggered bulk import, a browser-driven cursor loop that dies with the tab (`ImportClient.tsx:29-49`). The live DB proves the gap: **14 distinct Zenbooker jobs errored without ever creating a booking**, and **34 `job.service_providers.assigned` events were lost** because they referenced bookings we don't hold ("booking not found", latest today). Every failure mode in P0-1…P0-4 is unrecoverable without this backstop.

**Fix spec.**
1. Vercel cron (daily, e.g. 05:30 ET) hitting a new `/api/reconcile/zenbooker` route (CRON_SECRET-gated): page the Zenbooker REST API for jobs in `[today − 7d, today + 60d]`, diff `data.id` against `bookings.zenbooker_job_id`.
2. For each missing job: process it through the same code path as the webhook (`processJob`), logging `action='job.reconciled'`. For each mismatch in date/status (e.g. canceled in Zenbooker, confirmed here): flag `needs_review` and log `result='drift'`.
3. Report: write a summary row (counts) and surface "last reconcile + discrepancies" on Settings → Webhook Logs; alert (email or visible badge) when missing > 0.
4. Add a "replay" admin action on a `webhook_logs` row that reprocesses its stored `raw_payload` (the data is already there, `route.ts:84`).

**Acceptance criteria.**
- A job present in Zenbooker and absent in `bookings` is created within 24 h with full mapping resolution, and visibly reported.
- A Zenbooker-canceled job still `confirmed` locally is flagged within 24 h.
- Cron failures themselves are visible (last-run timestamp shown in Settings).

**Jest tests to add.** Reconciliation diff unit tests (set difference, canceled exclusion, window boundaries); replay endpoint reprocesses a stored payload idempotently (combined with P0-2's unique index).

### P0-6. Drop-off↔pickup linking: not implemented on the webhook path at all; import path links by address only; `needs_review` is effectively invisible

**Problem.** Linking exists **only** in bulk import (`app/api/import/zenbooker/route.ts:876-910`). A pickup arriving via live webhook is never linked — and webhook-side pickup *detection* rests solely on `customer_name === 'Wonderfly Games Pickup'` exactly (`webhookProcessor.ts:95`; the service-name 'Pickup' check at `:96` is dead code — it only runs when all services are in the 5-name delivery set, which excludes pickup-named services). The KB §9 algorithm (extract customer from service name; match per-customer; already-linked → needs_review) is **not implemented**: matching is exact-address only with no customer check and no lower date bound (`:887-890`), and the already-linked case stays `confirmed` (`:893-896`). Violations are real and current: live unmapped logs show "Lawn Games Pickup- Katie Mccoy" (customer *after* "Pickup"), "Akya Evans - Wonderfly Games Pick Up", "…Arena Return", "Foam Machine Pick Up - …" arriving daily. Consequences: dropped-off equipment treated as available (double-booking), or pickups importing as coordinated events that attempt equipment resolution. Meanwhile `needs_review` (39 rows live, 23 upcoming) surfaces only as a banner on `/bookings` (`BookingsClient.tsx:208-210`) — no sidebar badge, no schedule/audit marker; and `needs_review` bookings **do count in packing lists** with whatever partial items they have (`packingList.ts:51-53`).

**Fix spec.**
1. Run linking in the webhook `job.created` path (shared function with import).
2. Implement the KB algorithm: parse the customer name out of the pickup service name (tolerate "Pick Up", "Pick-up", "Return", name-before or name-after with a separator heuristic); match on (fuzzy customer ∧ exact address) within a bounded window (pickup date − 14 d); on zero or ambiguous match, or already-linked dropoff → `status='needs_review'` with a precise `result_detail`.
3. Broaden pickup detection: treat service names matching the pickup/arena-return pattern set as pickup-type in `resolveEventType` (move the v1 import patterns `route.ts:174-186` into the shared resolver), so convention-variant pickups stop landing as unmapped coordinated bookings.
4. Surfacing: sidebar badge on Bookings with the `needs_review` count; mark needs_review bookings visually on Schedule and 4-Week Audit.

**Acceptance criteria.**
- A webhook pickup with a convention-conforming name links bidirectionally to the right drop-off.
- Two customers at the same address: pickup links to the matching customer's drop-off, not the most recent.
- Convention-violating pickup → `needs_review`, visible as a sidebar badge without opening /bookings.
- The 39 existing needs_review rows triaged as part of rollout (one-time data pass).

**Jest tests to add.** Linking happy path; same-address two-customer disambiguation; already-linked → needs_review; address-mismatch → needs_review; webhook-path linking; name-extraction table test over the real variants observed in webhook_logs ("Lawn Games Pickup- Katie Mccoy", "Akya Evans - Wonderfly Games Pick Up", "Tonya Satchell- Lawn Games Return", "Foam Machine Pick Up - Jacqueline Klosterman").

### P0-7. Out-of-service is split across two systems; sub-item availability reads a dead counter — 11 OOS units invisible right now

**Problem (live-verified).** The app writes OOS incidents to `equipment_oos`; the counter triggers (`update_out_of_service_count`, `update_issue_flag_count`) fire on the **legacy** `out_of_service_items`/`issue_flag_items` tables. Equipment-level availability is safe (reads `equipment_oos` directly — `app/(dashboard)/availability/page.tsx:27`, wizard `route.ts:99`), but **sub-item availability uses the counter**: `availability.ts:184-187` (`s.total_qty - s.out_of_service - subBooked`). Live: `goal_set` (3), `small_black_air_pump` (6), `tripod` (2) have active OOS rows in `equipment_oos` with counters at 0 → invisible to packing/availability today. Equipment-level counters have also drifted (`arrow_tag` 0 vs 7, `bubbleball` 0 vs 1, `connect_4` 0 vs 1 in the legacy table; `laser_tag_lite` 0 vs 6 in `equipment_oos`) — the marketing `equipment_catalog` view even aliases the column `oos_count_legacy`. Two more rot vectors: resolving a flag as `moved_to_oos` **double-writes** (real row into `equipment_oos` via the modal + a second row into orphaned `out_of_service_items` via `issue-flags/[id]/route.ts:58` that no screen reads); and the trigger functions are not `SECURITY DEFINER`, so the embedded `UPDATE equipment` is subject to the admin-only RLS update policy — a non-admin DML path updates counters for **zero rows with no error** (classic silent drift). Bonus bug found en route: the sub-item OOS route inserts `quantity` rows then calls `.select().single()` (`app/api/equipment/sub-items/[subId]/oos/route.ts:22-31`) — any qty > 1 returns a 500 *after* successfully inserting, inviting retry-duplicates.

**Fix spec.**
1. Make `equipment_oos` the single source of truth. Change sub-item availability to consume active `equipment_oos` sums (the page already fetches them for equipment; extend the query to `sub_item_id`).
2. Remove the orphan write in `issue-flags/[id]/route.ts:56-66`; drop the dead `/api/out-of-service` routes, `useCreateOOS`/`useMarkOOSReturned` hooks, `OOSModal.tsx`, and the `out_of_service_items` realtime subscription (`useRealtimeSync.ts:37`).
3. Either retire the counter columns (preferred — nothing should read them; update `marketing_api.equipment_catalog` consumers to `active_oos_count` which the view already computes), or re-point the triggers at `equipment_oos`/`equipment_reports` with `SECURITY DEFINER` + pinned `search_path`.
4. **Reconciliation check (spec'd as requested):** a nightly job (same cron as P0-5) runs `SELECT e.id FROM equipment e WHERE e.out_of_service <> (SELECT COALESCE(SUM(quantity),0) FROM equipment_oos WHERE equipment_id=e.id AND returned_at IS NULL)` (and the sub-item/issue-flag analogues) and reports drift — until the counters are removed, after which the check is unnecessary.
5. One-time data repair migration: zero/true-up counters, close or migrate the 9 stranded `out_of_service_items` rows and 27 `issue_flag_items` rows (decide: migrate open ones into `equipment_oos`/`equipment_reports` or mark resolved).
6. Fix the multi-row `.single()` bug (use `.select()` without `.single()`, return the array/count).
7. Subscribe realtime to `equipment_oos` (currently a cross-user staleness gap — user B's open Availability page never sees user A's OOS entry).

**Acceptance criteria.**
- Marking a sub-item OOS immediately reduces its availability on the Availability page, across users.
- `goal_set`/`small_black_air_pump`/`tripod` show correct reduced availability after the data repair.
- Resolving a flag as moved-to-OOS creates exactly one OOS record.
- Sub-item OOS with quantity 3 returns 201 and creates exactly 3 rows (or one row qty 3 — pick one and assert it).
- Nightly drift check reports zero on a clean day.

**Jest tests to add.** Availability: sub-item active-OOS sum deducted (fixture mirrors the live goal_set case); `it('sub-item OOS reduces available_qty without touching the counter column')`. Route: sub-item OOS qty 3 → success + 3 rows. Resolve-flag moved_to_oos → single `equipment_oos` insert.

### P0-8. Three calculation bugs producing wrong loads or wrong wizard availability

**Problem — three independent code bugs in the math core:**

**(a) Coordinated sub-items shared across different parents take MAX instead of SUM.** `packingList.ts:119-123` maxes contributions across linked parents; physically both parents load simultaneously. Elite Laser Tag (1 set → 4 chargers) + Arrow Tag (2 sets → 8 chargers) sharing "Charging Station" packs 8, needs 12. The dropoff path sums correctly (`:114`); only the coordinated path is wrong. The existing multi-parent test covers only dropoff, masking it.

**(b) The wizard ignores dropoff→pickup spans entirely.** `wizardSlots.ts:158-163` checks only `event_date`/`end_date`; `linked_booking_id` is fetched (`route.ts:92`) but never used. 10 Cornhole dropped 6/10 with pickup 6/13 count as zero booked on 6/11–6/12 — sales books equipment sitting at a customer's site. (`availability.ts:74-79` handles this; the route comment claims only a month-boundary limitation, but the gap is total.)

**(c) Overnight webhook bookings block nothing in the wizard.** `calcEndTime` wraps past midnight (`webhookProcessor.ts:128-134`: 22:00+4h → "02:00") and the webhook always writes `end_date: null` (`route.ts:351`). The wizard then builds an inverted window `{start: 22:00−buffers, end: 02:00+buffers}` that can never overlap any slot (`wizardSlots.ts:186-193`) → the wizard offers every evening slot on a fully occupied chain. Side effects: `availability.ts:93-94` frees equipment the next morning even when the event ends ≥ 4 am, and `computeChainTimes` (`availability.ts:237-241,267`) loses midnight-wrapped window-end comparisons.

Related P1-grade item folded here because the fix is the same line of code: **(d)** coordinated MAX is computed per `booking_items` row, not per booking (`packingList.ts:71-74`) — one booking with two rows of the same item (base 10 + add-on 5) packs 10 instead of 15. Availability and wizard sum rows per booking; only the packing list disagrees.

**Fix spec.**
- (a) Per-parent coordinated contribution = `getEffectiveParentQty(parent, coordQty) × loadout_qty`, **summed** across parents (MAX stays where it belongs: across bookings of the same parent, already applied upstream).
- (b) In the wizard route, pre-expand each drop-off's effective range to its linked pickup's `event_date` (replicating `isBookingActiveOnDate`'s map-aware logic).
- (c) At the source: when the computed end crosses midnight, persist `end_date = event_date + 1` in the webhook insert/update. Defensively: anywhere `end_time < start_time` with null `end_date`, treat as next-day (`end += 1440`).
- (d) SUM rows per (booking_id, item_id) first, then MAX per-booking totals across bookings.

**Acceptance criteria.**
- Two coordinated parents sharing a sub-item: packed sub qty = sum of per-parent contributions.
- Wizard query on an intermediate dropoff↔pickup day shows the equipment as booked.
- A 22:00–02:00 webhook booking stores `end_date` next-day; wizard blocks the evening; availability counts 6/10 (and 6/11 only if end ≥ 4 am).
- One coordinated booking, item rows 10+5 → parent qty 15 on the packing list.

### P0-9. Webhook secret: logged in URLs, no replay protection, and full booking-overwrite blast radius

**Problem.** The secret rides the query string (Zenbooker limitation — accepted), which means **every delivery writes the live secret into Vercel request logs** (and any log drain); anyone with dashboard/log access holds it. Comparison is plain `!==` (`route.ts:35-39`), not timing-safe. The timestamp check is skippable by omitting `timestamp` (`:61-66`), so there is no replay protection. A holder of the secret can: overwrite any booking's fields and wipe/replace its items via `job.created` upsert keyed on attacker-supplied `data.id` (`:343-361`), or cancel the calendar wholesale via `job.canceled` (`:198-216`). Job IDs are enumerable from any prior log leak. Structural validation before processing is minimal (`data.id` string check only). Rotation today is lossy: between setting the new env var and updating Zenbooker, every webhook 401s with no log (P0-3) and no dual-secret window exists.

**Fix spec.**
1. Timing-safe compare (`crypto.timingSafeEqual` over SHA-256 of both sides).
2. Accept `ZENBOOKER_WEBHOOK_SECRET` **or** `ZENBOOKER_WEBHOOK_SECRET_PREVIOUS` to enable zero-loss rotation; rotate on a calendar cadence (quarterly) and after any log-access change. Document the rotation runbook (set new → update Zenbooker → clear previous → bulk import to backfill the window).
3. Replay/forge hardening rides on P0-3's zod validation and P0-4's transition guards (manual/`source='manual'` rows protected from upsert; canceled terminal). Add idempotency: dedupe on a Zenbooker event id if present in the payload, else hash of (action, data.id, timestamp).
4. Optional, zero-code: Vercel WAF rule restricting the webhook path to Zenbooker egress IPs if published.

**Acceptance criteria.**
- Replayed payload (same event identity) is logged `skipped`, processed once.
- `job.created` upsert cannot overwrite a `source='manual'` booking.
- Both current and previous secret validate during a rotation window; rotation drill performed once without data loss.

**Jest tests to add.** 401 on missing/wrong/empty secret; previous-secret accepted; replay → skipped; manual-booking overwrite refused.
